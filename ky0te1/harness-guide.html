ky0te1 と Hermes のハーネス・指示フロー

これは、どこに何があり、ユーザーの依頼がどの経路で別の作業者へ渡り、どの正本を直せば何が変わるかを読むためのローカル説明書です。設定値は確認時点の観測値であり、一般仕様・このホストの設定・改善案を分けて示します。

ハーネスは、LLM だけでなく、起動方法、profile、許可された tool、指示、Kanban、workspace と検証記録を組み合わせ、作業を安全に繰り返す周辺構成です。receiptは、誰が何をどの revision で検証したかを次工程へ渡す記録です。

3. 指示の読み込み・組み立て順と優先関係

「prompt に置かれる順」と「命令が衝突した際の権限」は別です。前者は以下の稼働 gateway v0.20.1 source の観測、後者は実際の message role（platform system/developer/user）と、このプロジェクトの運用契約で決まります。card や repo file は、ファイル種別だけでユーザーより上位にはなりません。

  1. gateway/CLI が profile home と config を解決して agent と tool schema を作る。run_agent.py:_build_system_prompt:4710–4713 が agent.system_prompt:build_system_prompt:798–824 を呼ぶ。
  2. 同関数は stable / context / volatile の三 tier を順に連結する。stable では profile home の SOUL.md（なければ既定 identity）、tool に応じた guidance、Kanban worker guidance、toolset と profile/home の案内を入れる（system_prompt.py:338–515, 587–650）。profile 名は権限の保証ではない。
  3. context tier では caller supplied system message があれば先に置き、続けて cwd の project context を探索する（system_prompt.py:696–726）。探索は .hermes.md/HERMES.md、root→cwd の AGENTS.md chain、cwd の CLAUDE.md、.cursorrules の最初に見つかった種別だけであり、PROJECT_GOALS.md は自動探索の対象ではない。必要な場合に project rule/card が読む（prompt_builder.py:2380–2449）。
  4. volatile tier は skills のindex、有効な memory/USER profile、external memory、plugin block、日付・model/provider を置く（system_prompt.py:728–789）。skill 本文は index と同時には読まれず、agent が skill_view を呼ぶ必要がある。
  5. Kanban worker の task 本文、同一 task の過去 run、完了 parent の summary/metadata、role history、comments は hermes_cli/kanban_db.py:build_worker_context:10619–10864 がこの順に整形する。dispatcher-owned worker guidance により最初に kanban_show を読む契約で、parent receipt は prompt assembly の固定 file 層そのものではなく、task context として取得される。
  6. この system prompt と user message を用い、agent loop が tool call と tool result を繰り返す。compression 後に prompt は再構築され得るが、同一 session 中に毎 turn 全 file を再読込する仕様ではない（system_prompt.py:798–816）。
衝突時に分けるもの扱い
message role の権限platform が渡す system/developer/user の実際の role と platform policy に従う。挿入順・path 名だけから優先度を推定しない。
project/card の運用契約ユーザーの目的を具体化する制約（scope、approval、JJ、receipt）として守る。ただし上位 role/policy と明示承認を越えない。
AGENTS と PROJECT_GOALSAGENTS は自動 project-context 候補、PROJECT_GOALS は本 repo のルールが必要時に読む正本であり、両者の読込契機を同一視しない。

未確認: この実行の全 prompt byte 列、外部 runtime/plugin の有無、compression 後の実際の再構成内容は取得していない。ただし、それを理由に上記の静的 source で確認できる探索順・tier・worker context の説明を「全て未確認」にはしない。変更前には公式 Prompt Assembly と、その時点で稼働中の package source を再照合する。

4. 一依頼の時系列と、別 worker に渡るもの

  1. 利用者が目的・制約・必要な承認を伝える。
  2. orchestrator が読取りだけで済むかを判断し、実装なら scope、base revision、workspace、implementation/review/decision cards を固定する。
  3. workspace helper が main の exact base から native JJ workspace を作る。
  4. dispatcher が dependency を満たす coder を起動する。coder は kanban_show、workspace 検証、実装、focused test、jj describe、receipt 付き完了を行う。
  5. coder 完了で reviewer card が解放される。reviewer は同一 card を引き継がず、receipt の full exact revision と直接親を基準に独立して APPROVE または REQUEST_CHANGES を出す。
  6. decision card の orchestrator が明示 APPROVE と revision、file list、test receipt を照合し、統合可否などの次の判断をする。
渡るもの渡さない／同一視しないもの
カード本文、親 receipt、exact revision、直接親、変更 file、test 結果、停止条件coder の会話全体、秘密、無関係な memory、暗黙の承認
workspace path と board 上の依存関係reviewer への coder model override の自動継承
明示的な APPROVE / REQUEST_CHANGESreview card が done という状態だけを承認とみなすこと

5. profile / model / provider / toolsets / skills / memory / context / approvals / board の責務

要素役割と境界
profile役割別の設定・指示・skills・memory を分離する単位。profile 名は権限の自動保証ではない。
model / provider推論先の既定値。カードの明示 override はそのカードだけに作用し、別工程へ機械的に継承しない。
toolsetsagent に提示する tool 群。Kanban worker では dispatcher-owned context と task 環境を条件に Kanban tools が露出する。
skills必要時に読む手順書。設定そのものではなく、実施方法を補助する。symlink が共有 dotfiles 正本を指す場合だけ実体を追う。
memory継続対話の補助情報。カードの durable receipt や repo 正本の代替ではない。
contextsystem/runtime/profile/project/card から組み立てられる実行時入力。常に全ファイルが無制限に投入されるわけではない。
approvals危険操作や protected/live 作業の別 gate。Kanban の完了や time-out で回避しない。
boardSQLite ベースの耐久的なカード・依存・receipt 境界。dispatcher が claim と起動を担う。

7. 重複・矛盾・脆弱な点と改善候補

事実: generic Hermes worker lifecycle には同一カードで review を依頼する選択肢もある。一方 ky0te1 は、事前作成した別 review card を coder 完了で解放する契約を AGENTS.md と profile 指示で追加している。この project-specific 契約を優先しないと reviewer lane が重複または停滞する。

事実: Hermes の一般的な Git worktree 機能と、この project の native JJ directory workspace は目的が異なる。この repo では Git linked worktree を使わないルールがある。

提案: profile 設定の allowlisted summary（profile、provider、model、toolsets、確認日だけ）を versioned な非秘密文書に自動生成せず、変更カードの receipt にだけ残す。設定の鮮度を示しつつ、秘密や設定全体の複製を避けられる。

提案: この HTML の「確認時点」ブロックには確認日と Hermes version を必ず更新し、値の変化を仕様変更ではなく観測値として扱う。

提案: 変更目的ごとに「正本・承認者・必要 test・戻す revision」を card body の最初に置く。memory や口頭経緯へ依存しない。

未確認: 実ブラウザでの desktop/mobile render と console error は、この作成時点では専用 browser 実行環境が未確認である。HTML parser による構造・anchor・runtime dependency 検査は別途実行する。

8. 用語

exact revision
短縮名ではなく、review 対象を一意にする Jujutsu の full commit ID。
direct parent
その change が直接基づく親 revision。差分の比較基準。
native JJ workspace
jj workspace add で作る作業ディレクトリ。ここでは repo 外の ky0te1-workspaces/ 配下に置く。
dispatcher
Kanban の ready card を claim し、指定 profile worker を起動する gateway 側の仕組み。
receipt
revision、親、変更 file、実行 command、結果、未確認事項を後工程へ残す記録。
approval
明示された許可。review card の done、timeout、無応答とは同義ではない。
